# Unused code and agent tool audit — LKM-235 (2026-10-11)

This is a source and contract audit, not usage telemetry. No public tool or compatibility path was removed. The earlier [retained helper review](UNUSED-HELPERS.md) records an explicit choice to keep some uncalled exports; findings below recommend later, separately reviewed deletion where appropriate.

## Reachability model

The shipped Bun roots are `src/native/index.ts`, `src/main/backends/provider-helper-entry.ts`, and the two preview scripts (`preload.ts`, `slow-motion-page.ts`) in `scripts/build-native.mjs`. `src/preview/states-frame.ts` is a runtime root too: `src/main/states-build.ts` bundles it into each states view (LKM-263). The Swift host and service source lists are explicit in that script. `bin/trezi` is the package binary; `bin/trezi-agent-mcp.mjs` is launched by `src/main/backends/codex-mcp.ts`. Unit and smoke roots live in `test/run.mjs` and `src/native/smoke-groups.ts`. A source import scan alone misses `NativeBridge`'s string event dispatch, service owner `case` methods, `#selector`/`NSSelectorFromString` AppKit callbacks, injected preview globals, and MCP tool names. None of those were treated as dead solely for lacking imports.

For tools, the chain is provider registration (`src/main/backends/claude.ts` or `bin/trezi-agent-mcp.mjs`) → provider/Swift grants (`src/main/provider-policy.ts`, `src/service/ProviderPolicy.swift`) → Claude's `sessionTool` or Codex's authenticated `trezi-agent-tools.ts` socket → `runTreziTool` in `session-tools.ts` → owner/preview implementation. `codex-mcp.ts` checks its required list and calls `workspace_state` at startup. `test/provider-helper-tools.mjs` exercises the helper/owner round trip with stand-in CLIs, and `test/trezi-agent-tools.mjs` checks the socket names. This proves routing in those fixtures, not real-world invocation frequency.

## Tool classification

**(a) Never registered for a provider.** Codex does not register Claude's `install_skills`, `list_recommended_skills`, or six pure design calculators. Claude does not register Codex's `workspace_state`/`prepare_conflict_resolution`. These are documented provider differences in `docs/PROVIDERS.md` (Audit table), not dead implementations. `install_skills` is still reached from Claude through `session-tools.ts:349`; the pure calculators run in its helper. The Swift grant list is a policy superset and is not itself a registration list.

**(b) Registered with broken routing.** None confirmed in the inspected contracts and fixture paths. `SESSION_TOOLS` contains the session-scoped registered names; preview names dispatch to `observeAgentPreview`/`runPreviewAgentTool`, other actions to their owners. The Codex required-name and authenticated `workspace_state` startup check and the provider-helper test cover the main failure modes. A real provider invocation could still expose an untested route.

**(c) Registered and valid without observed production use.** The registered Claude and Codex tools, including `chat_island`, `preview_interact`, states canvas, Publish/Git, and Gen UI, remain reachable through the chain above. Source or test logs are not a usage census. Recommend telemetry from explicitly redacted tool names over a defined period if product wants usage-based retirement; do not remove them on this evidence.

### Broken advertised capabilities

None confirmed. Provider-specific absences in (a) are not advertised for that provider in `docs/PROVIDERS.md`. If a future contract check finds a registered name missing from the bridge or an owner rejects a valid call, file that as a routing bug, preserving the public tool while fixing its path. A useful follow-up is one automated contract comparison across provider registrations, Codex required names, `TREZI_AGENT_ACTIONS`, `SESSION_TOOLS` and the Swift grants; keep it separate from LKM-234's CI work.

## Verification and boundaries

This documentation-only audit makes no implementation change. Focused source searches, the build root lists, provider contracts, legacy audit and retirement census informed the classifications. The quick verification result is recorded in the LKM-235 progress entry. No native group is implicated by a runtime edit, and no real provider or keychain interaction was used. A static inventory cannot prove a dynamically invoked callback never fires or a valid tool never gets used.
