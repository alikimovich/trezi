# Agent browsers (LKM-212)

Each chat or background agent gets a private WebKit page when it first calls a preview tool. The page is a `WKWebView` owned by the native host, attached outside the window without focus. It uses the same `TreziPreview` and `TreziAgent` content worlds as the visible preview. The host discards all page-to-app IPC from an agent browser. Media permission requests are denied. Main-frame navigation stays on the assigned local dev-server origin.

`open_preview`, `reload_preview`, and the `preview_*` observers default to that page. Its route, scroll, viewport, console and animation speed belong to the agent session. A session working in the live checkout gets a page on the visible dev server, and its identity includes a session-specific suffix, navigation count, document start and the live HEAD sampled at navigation. A session in its own worktree (LOCAL-WEBKIT-1) gets a page on a private runtime for that worktree instead (see [private agent runtimes](#private-agent-runtimes)), so its unlanded edits render without `land_now`. Three pages may exist at once. They close after two minutes idle and when explicitly released. A fourth agent receives a limit error. `reload_preview` loads the agent page again (`AgentBrowser.open(path, { reload: true, hard })`; `hard` clears WebKit's caches first). A failed load in an agent page answers only the agent's tool call; it never reaches the user's activity or the preview's load-error UI.

`target: "user"` reads or changes the visible preview. Navigation, viewport and speed changes require five seconds without user input in Trezi. Agents should use it only when the user asks to see the page or the result needs visible rendering. Offscreen snapshots use `WKWebView.takeSnapshot`; Liquid Glass/backdrop and some GPU effects may not paint. A check requiring those effects must be named as a visible-rendering check.

`engine: "chromium"` is an optional adapter slot. The agent browser interface is shared across engines; the Chromium factory can be registered when the external `agent-browser` CLI and Chrome for Testing are installed. WebKit is always available with Trezi. A missing adapter returns an explicit error. No Chromium download runs as part of Trezi's normal build or preview.

Vercel agent-browser remains required for browser verification during UI changes. Trezi's provider helpers put the managed wrapper's folder first on PATH and append the directory of the helper's own Bun so the wrapper's `env bun` shebang resolves under the helper's system-only launch PATH. Since LOCAL-WEBKIT-4 the build copies the wrapper, `bin/trezi-browser-tools.mjs` (detection), the guard and the policy into `Trezi.app/Contents/Resources/browser/bin` before signing (`scripts/package-managed-browser.mjs`), and the bundled backend and provider helper resolve only that copy (`managedBrowserRoots` in `src/main/backends/managed-browser-path.ts`, from the bundle banner's `__treziResources`). The checkout's `bin/managed` is used only by a source run (`../../bin` or `../../../bin` from the base), so a built or moved app needs no checkout for the launcher route.

### Setup: Settings → Browser Checks (LOCAL-WEBKIT-4)

Built-in WebKit (the visible preview and agents' private pages) needs nothing external and always reads Available. The agent-browser CLI and the dedicated Chromium headless shell stay external: the pane (`src/native/settings-browser.ts`, model `src/main/browser-setup.ts`) shows the Chromium checks as Not Installed, Partly Installed, Not Checked, Ready, Check Failed or Unsupported, with each tool's version, path and source (Trezi's folder, PATH, the shared Playwright cache), the Node/npm/npx/Homebrew prerequisites, what each tool enables, the copyable commands and the official links (`BROWSER_TOOL_COMMANDS`/`BROWSER_TOOL_LINKS` in `bin/trezi-browser-tools.mjs`).

- **Tested pair.** agent-browser 0.26.x with headless shell 149.0.7827.55 (Playwright revision 1228). Newer CLIs (npm latest 0.39.1 needs Node 24 and pnpm 11) are shown as untested and never launched; Trezi's own 0.26.0 wins over them. The shell command is `npx --yes --package=playwright@1.64.1 playwright install chromium-headless-shell --no-remove` (Node 20+); `agent-browser install` downloads Chrome for Testing, which the wrapper never uses.
- **Installs.** Only when the user presses Install, through the platform owner (`src/service/BrowserTools.swift`, `browserToolsInstall`/`browserToolsCancel` in `docs/SWIFT-BACKEND-PLATFORM.md`): a fixed npm or npx argv found on fixed folders, into `~/Library/Caches/Trezi/browser-tools` (0700), with an allowlisted environment, redacted bounded progress, Cancel that signals the process group, and no sudo, Keychain or shell profile. Other tools' caches are only read, never pruned. Nothing installs at startup or because an agent asked.
- **Ready.** Only from a check that runs the packaged wrapper (`open about:blank`, `get url`, `close`) and finds a fresh headless-shell process launched with this run's private profile. An install, a changed version or a failed install clears an earlier Ready; a reply from an older daemon's browser fails the check. The binding includes each tool's executable identity (device, inode, size, mtime), taken before the launch and compared after it, so replacing a file at the same path and version drops Ready, also when it happens during the check. `get url` must exit 0 and `close` must succeed; otherwise the check fails, its own headless-shell processes are killed (only those naming its `tzab-` folder) and the folder is removed once none is left, or kept as evidence if one still runs. The message never claims the agent-browser daemon stopped: it exits after its idle timeout, or run `agent-browser close --all`.
- **Bounded probes.** Every version probe runs in its own process group and is SIGKILLed at a limit (8 s; node 5 s), as are the wrapper's `--version`/`--help`/`skills get` passthroughs: a tool that ignores SIGTERM cannot stall detection or Settings.
- **Repair.** A headless shell that is present but reports no version, or failed the last check, shows Repair Headless Shell (no shell: Install). The install removes Playwright's `INSTALLATION_COMPLETE` marker in Trezi's own cache first, since Playwright skips a revision that has it. The install refuses a linked, non-folder or foreign-owned folder anywhere from `~/Library` to the destination before starting.
- **Tests.** `test/browser-setup.mjs` (states, prerequisites, retry, stale daemon, no false Ready), `test/browser-tools-install.mjs` (the Swift installer with scripted npm/npx: argv, env, redaction, cancel, retry), `test/browser-setup-packaged.mjs` (a relocated copy of the built app with no checkout or CLI: WebKit linked, the packaged detection, the wrapper's dependency exit and its route with scripted tools) and native smoke `browser-setup` (`src/native/smoke-browser-setup.ts`: the pane pressed through missing, partial, installing/Cancel, failed, retry and a real Check Again that must reach Ready).

PATH alone is not the route (LKM-269). A provider shell run as a login shell (Codex's default) lets macOS path_helper and the user's profile reorder PATH, so a global `/opt/homebrew/bin/agent-browser` can win. The route is the explicit, app-owned absolute path to the wrapper, `managedBrowserWrapper(base)`: the same two bases, only if the file exists and is executable, exported as `TREZI_AGENT_BROWSER`. The helper sets it in its own environment at start (`provider-helper-entry.ts`), and each provider re-applies it on every turn, so a reused or resumed helper keeps it:

- **Codex** (`managedBrowserCodexConfig`, merged in `codex.ts` `openThread`, which first turns and resumes both use): `shell_environment_policy.set` with the managed PATH and `TREZI_AGENT_BROWSER`, `allow_login_shell=false` (both keys exist in the pinned CLI) and a PreToolUse command hook, `bin/trezi-browser-guard.mjs`, beside the Git guard.
- **Claude** (`claude.ts`): the query's `env` carries the same two variables, and the existing PreToolUse Bash hook calls `managedBrowserRefusal`. Claude's Bash tool snapshots the user's shell, so the hook and the absolute path are the guarantee, not PATH.
- **Policy** (`bin/trezi-browser-policy.mjs`, shared): the only absolute path allowed is Trezi's wrapper (`"$TREZI_AGENT_BROWSER"` or its literal path). A bare `agent-browser` (also behind `env`, `bash -c`, `npx`…), any other absolute or relative path to a CLI, reassigning `TREZI_AGENT_BROWSER`/`PATH` for it, the wrapper's forbidden flags (`--headed`, `--executable-path`, `--profile`, `--cdp`, `close --all`…) and a system Chrome app path are refused with the way back. `command -v`, `which` and `echo` stay allowed. The wrapper still enforces the flags itself.
- **Errors**: the wrapper exits 2 for a route or policy refusal and 3 for a missing dependency, with `dependency: vercel-cli` or `dependency: headless-shell` and install guidance. A route problem never tells the user to reinstall a browser, and a global CLI on PATH is only the engine behind the wrapper, never a managed-verification pass. There is no WebKit, `preview_evaluate`, headed or system-Chrome fallback.
- **Tests**: `test/managed-browser-path.mjs` runs real `/bin/zsh -c` and `-lc` (a throwaway ZDOTDIR mimics the login-shell PATH reorder) against the bundle and source bases with a global CLI earlier on PATH; `test/managed-browser-provider.mjs` checks Claude and Codex first and resumed turns, replaying the Codex config through the real SDK into a fake `codex` binary; native smoke `managed-agent-browser` repeats the shell check beside the unchanged focus evidence.

This wrapper uses the installed CLI with a dedicated `chrome-headless-shell` executable, private HOME, temporary directory and profile for each named session, a private config, and `--headed false`. It refuses a system Chrome fallback, external CDP attachment and overrides that could expose a GUI browser. If the CLI or headless shell is missing, it reports the dependency instead of installing it or substituting WebKit. The CLI's daemon can be reused within a session and is given a two-minute idle timeout. The optional in-process Chromium adapter remains unregistered; the managed CLI is the required Chromium path.

Native smoke records passive frontmost PID, key window, first responder, activation notifications and cursor coordinates around private WebKit operations. A separate managed-CLI fixture checks the actual Chromium path. No focus restoration runs after browser commands.

The host commands are `agentBrowserCreate`, `agentBrowserOpen`, `agentBrowserSpeed` and `agentBrowserClose`; Bun owns session reuse and idle cleanup in `src/main/agent-browser.ts`. The visible preview remains the only source of editor selection and overlay IPC. Native smoke `agent-preview` checks two independent sessions, the cap, an offscreen screenshot, and that the visible URL, width, scroll, selection and focus remain unchanged.

## Private agent runtimes

LOCAL-WEBKIT-1. A WebKit page whose session root is not the live checkout (a per-chat or background-agent worktree) loads from that worktree's own dev server. The engine path for `engine: "chromium"` and the agents' own managed `agent-browser` CLI calls are unchanged and still serve the live checkout; only `preview_verify` engine `"chromium"` ([verification receipts](#verification-receipts-and-refs)) runs against the private server.

- **Owner.** The Swift RuntimeOwner runs it as a private runtime: a `start` with an `agent` id, keyed `agent:<id>:<root>` apart from the visible server (`src/service/RuntimeServer.swift`). It is supervised, loopback-only and on its own reserved port, like the visible one. At most three run at once (`busy` after that). Its logs and exit events carry `agent` and `generation` and reach only the agent listeners in `src/native/runtime-service.ts`, never the preview, activity or the selected project. Details: `docs/SWIFT-BACKEND-RUNTIME.md`.
- **Setup.** The command and framework come from the worktree's own detection. A custom command the user set for the visible preview is not reused, and setup-required, non-web and Swift projects are refused. The server uses the worktree's own `node_modules`, framework cache and the `.env` link that worktree creation already made. No install runs and nothing else is copied.
- **Registry.** `src/main/agent-runtime.ts` keeps one runtime per private page id. Concurrent opens share one start, and a port `conflict` is retried once. A runtime for another root is stopped, not reused. `stopAgentRuntime` cancels a start in flight at once (the owner is told to stop the agent without waiting for it) and a late answer registers nothing. Bun start calls `stopAgents()`, so a previous Bun's runtimes are never adopted.
- **Cleanup.** A runtime stops when its page closes (two-minute idle, release, `closeChat`/`closeSession` through `releaseAgentBrowsersFor(root)`) and when Trezi quits (`stopAll`). The service's process journal reaps them after a service crash. Closing a page during its server's start cancels that start immediately and the late answer neither registers a runtime nor reopens the page (`open` then fails with "The agent browser was closed."). An `open` on a page that is already closed or released fails before it starts anything. A session that closes while its page is still being created (`releaseAgentBrowsersFor` also marks pages in creation) has that page closed on arrival, never published, so no tool can start a server on it; a call for the same page meanwhile waits for that close and opens a fresh page. A page that is being closed is waited for the same way: `closeAgentBrowser` keeps a per-name closing promise, so a reopen of the same key and checkout never starts before the old teardown (which stops the runtime and drops the `agent:<id>` view under the same deterministic id) has finished and cannot clobber its replacement. A page with an `open` in flight (a private start waits up to 150 s) is busy, so the idle timer re-arms instead of closing it. A crash of the server itself is recorded, and the next call starts a new generation. Visible servers are never stopped by any of these.
- **Identity.** The `preview` identity in `open_preview`, `reload_preview` and `preview_*` answers gains `runtime` (`kind`, `agent`, `root`, `url`, `generation`, `ended`) and `source` (`served`, `current`, `head`, `dirty`, `verified`, `reason`) from `src/main/agent-identity.ts`. `source.verified` holds only when the server, generation and origin are still the ones the document loaded from, the document is the page's last navigation (same `timeOrigin`), and the worktree's exact source snapshot (`src/main/source-snapshot.ts`: HEAD plus the bytes of every changed and untracked file, excluding `node_modules` and `.env`) was equal before the load, after it and now. A changed path that is a directory (a dirty submodule or an embedded repository) or a special file has no bounded exact identity, so the snapshot fails closed with `unsupported-entry` (no id, nothing verifies) instead of one constant standing for contents that can change. Otherwise `reason` names the first failure: `not-loaded`, `runtime-stopped`, `runtime-restarted`, `unknown-navigation`, `document-replaced`, `snapshot-unavailable`, `changed-during-load` or `source-changed`. Live HEAD is never consulted, and hot reload is not counted as verification.
- **Landing contract (task 3, not implemented here).** A landing gate may treat a private check as evidence for exactly one worktree state: `runtime.kind === 'private'`, `source.verified === true`, and `source.served` equal to the snapshot of the tree being landed, with `runtime.generation` unchanged since the check. Private pages do not feed `noteServedRevision`/`saw()` in `src/main/session-tools.ts`, so they never count as having seen the live checkout.
- **Proof.** `test/runtime-owner.mjs` (`private agent runtimes`) runs the real Swift owner. `test/agent-runtime-isolation.mjs` covers the snapshot, the registry (including a stop during a delayed start, idle expiry with an `open` in flight a close during a pending start, release during page creation and `open` after close over a fake host) and every identity reason. Native smoke `agent-runtime` (`src/native/smoke-agent-runtime.ts`) serves two worktrees with different uncommitted content on two private pages while the user's page, server, selected project and focus stay unchanged.

`preview_interact` (LKM-230) uses the agent page: `click` (a `selector` plus `index`, a `source` stamp or `x`/`y`), `type` (`text`, `clear`), `press` (`key`, optionally on a `selector`), `hover`, `scroll` (`deltaX`/`deltaY`, `to: "top"|"bottom"` or into view), `select` (`option` by value or label) and `wait` (a `selector`, `hidden`, `text` or `networkIdle`, up to 15 s). `target: "user"` is refused: interaction never drives the user's preview. The page side is `src/preview/agent-interact.ts` in the isolated world; it synthesizes DOM events (so click activation, input and key handlers run, but CSS `:hover` does not apply) and refuses file inputs, `download` links, links and forms that leave the dev server origin, and forms posting to other hosts. The host is the backstop: `agentPolicy` in `src/native/PreviewPlatform.swift` blocks off-origin main-frame navigation, external form submission, new windows and downloads (including responses WebKit cannot show) for `agent:` views only, and emits `agent-navigation` events (`start`, `blocked`, `failed`) that `src/main/agent-browser.ts` keeps as `loading` and `notices`. `src/main/agent-interact.ts` validates the request, waits up to 10 s for a navigation the action started, and answers JSON with `ok`, the resulting `url`, `navigated`, any `blocked` notices and the console errors since the action, plus a 480 px JPEG unless `screenshot: false`. Network idle counts the page's `fetch`/XHR through a page-world counter installed in agent pages only. Fetches to other hosts are not blocked, and there is no per-user allowance for leaving the origin yet. Native smoke `agent-interact` drives `filter.html` in the fixture (filter click by selector and by source, type, select, hover, scroll, waits, a same-origin form) and checks each refusal and host block, and that the user's preview is unchanged.

## Verification receipts and refs

LOCAL-WEBKIT-2. Agents assert what a page does with `preview_verify`, and the host (never the agent or the page) decides and records the result.

- **Refs.** `preview_interact` action `refs` lists the page's interactive elements and headings (or a `selector`'s matches, `limit` ≤ 150) with a ref such as `1a2b3c4d:e12`. `src/preview/agent-observe.ts` keeps ref → element in a WeakMap in the isolated world, behind a random per-document id that never leaves the host. `src/main/agent-refs.ts` scopes each token's nonce to one agent page, its navigation count and that document id. A ref from another session or a closed page ("was not issued by this session's agent browser"), from an earlier navigation, or for a removed element is refused as stale. A ref is never re-resolved by a selector. `click`, `type`, `press`, `hover`, `scroll`, `select`, `wait` and checks take `ref` in place of a selector.
- **Viewport and theme.** In an agent page, `preview_viewport` sets the offscreen view's own CSS size (`width`, `height` 240–2160, presets) and appearance (`theme` light/dark/system, an `NSAppearance` on that view only), via `setAgentViewport` in `src/native/PreviewAgent.swift` and `src/main/agent-viewport.ts`. `restore: true` returns to 1280×800, system. The user's preview is never resized or recolored. A user-target viewport still takes only a width and refuses `height`/`theme`. This is emulation in WebKit on this Mac: no device pixel ratio, touch, UA or OS change.
- **Fidelity.** Every `preview_interact` report carries `fidelity` (`synthetic-dom`, `trusted: false`, `cssHover: false`). Synthetic events run the page's handlers but never set `:hover`, `:active` or `:focus-visible`. A WebKit check whose selector uses one of those is refused, with a pointer to engine `"chromium"`. A key whose WebKit default action is not emulated (Cmd/Ctrl shortcuts, Option editing, Enter in a textarea, word deletion, caret and selection keys, page scrolling) is refused after the handlers ran (`unemulated`, `handlersRan: true`), instead of reporting a press that did nothing.
- **Checks.** Checks are declarative (`src/main/browser-checks.ts`): `exists`, `absent`, `visible`, `hidden`, `text`, `value`, `attribute`, `count`, `state`, `style`, `url`, `title` and `noConsoleErrors`. They use `equals`/`contains`/`min`/`max` and take no expressions, regexes or page code. There are at most 20 checks, text up to 1,000 characters, an optional condition wait `timeoutMs` ≤ 10 s each and 30 s in total. Up to 10 setup `steps` are `preview_interact` actions (`src/main/verify-args.ts`). The page reports raw facts only, through the isolated-world observer. `judge` decides each check in Bun. An unreadable fact fails, and password values are never read.
- **Receipts.** `src/main/preview-verify.ts` writes one receipt per run (`src/main/verification-receipts.ts`). It records:
  - the engine and input kind;
  - coverage: engine, macOS version, emulated viewport and scheme, and `notCovered` (Windows, Android, iOS, real devices, other browser versions);
  - the runtime (`kind`, `agent`, `root`, `url`, `generation`);
  - the exact source snapshot, HEAD and dirty count;
  - the document (URL, navigation, `timeOrigin`);
  - the requested viewport and, for WebKit, what the page itself reported (`viewport.measured`: `innerWidth`, `innerHeight`, `prefers-color-scheme: dark`);
  - each step and check with expected and actual values (actual values clipped to 500 characters);
  - the screenshot artifact with its path, SHA-256, bytes and size.
  The screenshot is written 0600 into a 0700 per-session directory under the temp dir. `verified` needs every check to pass, a private runtime, a verified source identity before and after, the same snapshot and generation, no navigation or document change during the checks, the page reporting the requested size and scheme (`viewport-not-applied` otherwise), and the screenshot. Otherwise `reason` names why. A page that does not show the current source is reloaded once before the steps. Each session keeps its 20 newest receipts, deleting evicted artifacts, and lists only its own. `list: true` re-checks each receipt against the current snapshot, generation and page: `source-changed`, `runtime-stopped`, `runtime-restarted`, `navigated`, `document-replaced` or `page-closed` make it no longer `current`. A session in the live checkout gets honest but never-verified receipts (`live-server`), because the visible server has no private generation or exact-source record.
- **Managed Chromium.** `engine: "chromium"` runs the same checks through Trezi's managed wrapper only (`src/main/verify-chromium.ts`, `src/main/managed-browser-cli.ts`). There is a `--version` probe first. A fresh `trezi-v<random>` session opens the session's own private server URL (the live server for a live-checkout session), sets the viewport and `set media`, and reloads. Steps (`click`, `type`/`fill`, `press` after `focus`, `hover`, `select`, `wait`) use trusted CDP input, and selector and text waits are polled by the host. Facts come from `get`/`is`/`errors`/`console` JSON on stdout and are judged by the same `judge`. The run ends with a PNG `screenshot` and always a `close`, which removes the private base. CLI stderr (for example "startup options ignored") is counted as CLI warnings in `engineDetail`, never as page errors or success. A JSON shape the parser does not recognize fails the check. The page leaving the server's origin stops the run. After the setup steps the host pins the checks to the page's full URL (path, query and hash, read with `get url`), re-reads it every round and after the checks, and any difference stops the run as failed (`the page navigated during the checks`), so a same-origin route change cannot pass as the page that was checked. The receipt's `document.url` is that pinned URL. Every wrapper call is bounded: one run budget (`RUN_BUDGET_MS`, 150 s) is split into per-call timeouts of at most the time left, a wait step keeps its own `timeoutMs`, and a check round keeps the 30 s check budget, so a hung or slow CLI cannot hold a run. On a call's deadline the wrapper gets SIGTERM, then SIGKILL to its own process group about a second later, and the call settles even if the child does not exit; only the wrapper and the CLI client it started are signalled, never a daemon the CLI detached or any unrelated process. A wrapper exit 3 returns `needs a dependency: vercel-cli|headless-shell: …` with no receipt and no fallback, while WebKit checks still work. There are no headed, CDP-attach, profile, download, cookie, storage or eval commands. The receipt binds the same snapshot and generation and the pinned URL, but not a document identity (`navigation` and `startedAt` are `null`): the wrapper offers no eval, so a replacement of the document at the same URL (a reload) cannot be seen.
- **Rules.** `src/main/rules.ts` asks agents to report the receipt id and whether it verified, never a pass it did not record, and to say that a Mac engine with an emulated viewport is not Windows, Android, iOS or device coverage. `preview_verify` does not replace the required Vercel agent-browser checks below; it adds a host-recorded receipt beside them.
- **Grants.** `preview_verify` is a session tool (`src/main/session-tools.ts`), granted through `src/service/ProviderPolicy.swift`, `src/main/provider-policy.ts`, Claude's in-process server and the Codex MCP bridge like `preview_interact`, and not read-only. Utility calls get none of them.
- **Residual limits.**
  - Synthetic WebKit input is not trusted input (no `:hover`/`:active`, no native default actions beyond the emulated subset), so use engine `"chromium"` for those.
  - Offscreen captures cannot paint Liquid Glass, backdrop or some GPU effects.
  - Console errors come from the page-world console forwarder, which page code could suppress, so `noConsoleErrors` holds only within that limit.
  - Hot-reloaded state and ignored files are outside the snapshot (LOCAL-WEBKIT-1).
  - A Chromium receipt cannot see WebKit's navigation or document: it is bound to the source, the server and the pinned full URL, so a same-URL document replacement is not detected.
  - Receipts and their screenshots are temporary evidence in memory and the system temp folder, released with the session that made them: `closeChat`/`closeSession` clear `receiptSession(emitKey, projectKey(root))` of the closing session only (`releaseSessionReceipts`), never every session on its root, because chats without a worktree share the live root; a Trezi crash leaves the temp folder to the system. They are not read by landing or recovery.
  - The CLI wrapper is run with Node `child_process.spawn` from the Bun backend (a retained helper-class module, see the census row), not through the Swift service: it is a pure assertion/evidence runner that writes nothing to the target and nothing outside the system temp folder, and every run ends with its own `close`. Moving it behind a service grant is not part of this ticket.
  - Neither engine is another OS or device.
- **Proof (bounds).** `test/browser-verify-bounds.mjs` (unit) runs a fake wrapper that ignores SIGTERM and has a grandchild that does too: the call settles inside its deadline plus the kill window and no process survives; a hung read stops a run inside its budget and a wait step at its own `timeoutMs`; a check round that never answers is abandoned at the total budget; a route change before a round or after the checks stops a Chromium run; refs of a current document survive more than 200 other scopes; and `releaseSessionReceipts` removes a closed session's receipts and artifact folder but not those of another chat on the same root or of the same chat in another checkout. `test/agent-runtime-isolation.mjs` also holds a page's close at the host and shows a concurrent reopen waits, keeping its runtime and view, and shows a changing nested repository fails the snapshot closed.
- **Proof.** `test/browser-verify.mjs` (unit) covers:
  - check limits and engine refusals;
  - verdicts;
  - condition waits on a fake clock;
  - argument refusals;
  - receipt invalidation, eviction and session separation;
  - CLI parsing;
  - the real wrapper with a missing CLI and with a fake CLI (warnings, an ambiguous answer, a failed step, leaving the origin);
  - the live-server receipt.

  `test/agent-interact.mjs` covers ref scoping. Native smoke `agent-verify` (`src/native/smoke-agent-verify.ts`) runs in a scratch worktree on its private server. It checks:
  - a verified dark 390×700 WebKit receipt with a condition wait;
  - a refused `:hover` selector, and a hover step that honestly fails a hover-only menu;
  - refs refused across sessions and stale after a reload;
  - receipts going `navigated` and then `source-changed` after an edit, with a fresh verified receipt for the new source;
  - a managed Chromium receipt with trusted hover on the same server and snapshot;
  - the user's preview unchanged throughout.

  It copies receipts and screenshots into the run's artifacts (`agent-verify/`).

## Landing checks

LOCAL-WEBKIT-3. Receipts are also what lets work land: a chat's or a spawn's work reaches
the live checkout only when a host check passed on the exact source tree that would land
([integration gate](../WORKTREES.md#integration-gate-local-webkit-3)).

- **Which check.** A web project needs a verified `preview_verify` whose private server
  has not restarted or stopped since. Projects without a web preview use `run_checks`
  (`src/main/command-checks.ts`): up to four of the live checkout's own `package.json`
  scripts (`bun run <name>`; refused when the chat changed the script or its `pre`/`post`
  hook), or `swift-build`/`swift-test`, each with a deadline (default 5 min, at most 15,
  cancelled with the session), a minimal environment and a 4,000-character output tail
  in its receipt. A run
  that changes the source fails. `list: true` names the checks.
- **What the agent sees.** `workspace_state.landingChecks` gives `ready`, the `need`, the
  `sourceTree`, the reason and the receipts it counted; `land_now` returns the same
  reason when it held. Rules tell agents to check after their last edit and never call
  held work landed.
- **Browser state.** Each agent page and the user's preview have their own non-persistent
  WebKit data store (`src/native/Host.swift`): cookies, `localStorage` and
  `sessionStorage` never cross between them, and a landing's reload of the visible
  preview keeps the user's. The native `agent-integration` smoke sets distinct markers in
  all three pages and checks them before and after landing.
- **Limits.** The private server shares the project's `.env` link, databases and remote
  services, and navigation limits do not stop `fetch`/XHR or server-side effects: a check

  code with the user's permissions, like the dev server.
