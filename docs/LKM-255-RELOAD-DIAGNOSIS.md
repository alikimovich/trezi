The manager's `verification.log` in artifact `6044c8ae-ba63-4b47-ace2-39e7d242d00a` reports 44 passed, 5 failed and 4 skipped. `chat-islands`, `layers-island`, `text-edit`, `editor-freshness` and `states-workbench` failed on preview updates. Artifact `39cbd344-8b1a-4d1e-a7f5-8c49c2e8b998` contains only a failed quick run, so it cannot locate a native reload stall.

The same reload waits also fail on LKM-269 (no Swift changes) and LKM-267 based on main `128ba9d`, according to the manager's comparison. Main has the same `StaticSite` watcher/broadcast path (`src/service/StaticSite.swift:66-108,265-295`). Its `StaticServer.serve` still held each SSE connection with a blocking read (the code replaced on this branch at `src/service/StaticServer.swift:98-115`); that can starve the dispatch pool once enough streams accumulate. The branch's dispatch-source hold and 82-stream `runtime-owner` regression remove that demonstrated mechanism, yet the reload failures recur here. The evidence therefore shows a broken or delayed **end-to-end reload** on main-based runs and on this branch; it does not prove which remaining stage is slow or whether host scheduling is the cause. Load averages alone cannot make that distinction.

There is one narrower stage-level reproduction in this diagnosis pass: `agentos verify quick` failed `runtime-owner` at `a watched change`. ## Why `scripts:["","",""]` is informative

`src/native/smoke-fixture.ts:26-31` creates two inline `<script>` elements. `StaticSite.snippet()` adds a third inline reload script (`StaticSite.swift:34-39`). `src/native/smoke-islands.ts:45-46` writes `island-light.js` and appends `<script src="/island-light.js">` to `index.html`, then waits for the card at lines 47-74. The failure probe at lines 52-54 maps every script to `.src`; inline scripts therefore yield `""`. Three empty URLs with `ready:"complete"` match the *old* served page, with its reload snippet present but without the newly appended external script. This does not show an island script failing to inject or run after a successful reload. To distinguish those possibilities on the next run, record the served page version, `index.html`'s on-disk script tag, SSE client state and the preview's `document.scripts` together at the timeout.

## Fix direction and verification

First add bounded, test-only diagnostics at the service/runtime boundary: last watcher event and path, site version, last broadcast version/result, and active SSE client count. At a failing native wait, capture those values with the page's URL, `document.readyState`, injected page version, EventSource `readyState`/last message, and a navigation count. Do not log file contents or prompts. The `runtime-owner` failure gives the watcher stage a concrete lead, while native diagnostics will confirm whether that is also the stage in the desktop runs. Do not increase smoke waits or rewrite files to force an event.

For successful **service-owned** writes, a direct `RuntimeOwner` → `StaticSite` notification after `SourceStore.transact`/Undo/file operations is a sound deterministic improvement: the service already knows the write succeeded, so preview invalidation need not depend on FSEvents. Add a service fixture that starts a real `StaticSite`, performs a source transaction, and checks version/SSE delivery without calling `changed()` in the test. Deduplicate the subsequent FSEvents callback for that same write; otherwise one edit can cause two reloads and spill into the next check. This alone is **not a complete fix** for the observed `text-edit` first wait, `chat-islands` initial script write or `states-workbench`, because those fixtures write directly from Bun (`smoke-legacy-project.ts:21-33`, `smoke-islands.ts:45-46`, `smoke-states-workbench.ts:90-98`). External filesystem changes still need reliable watcher delivery or a bounded fallback that detects content changes under the root. Cover that separately with a runtime-owner test using an actual watched write (not a manual `changed()`), asserting that the SSE version arrives and that a newly fetched page contains the changed content. Then check browser reload in native smoke without the reverted touch harness.

The next repair session should inspect the diagnostics on main `128ba9d` and on this branch in the same time window, implement the fix at the first stalled stage, run quick verification, then native groups `core,islands,shadow-light`. `core` contains `text-edit`, `layers-island`, `states-workbench` and `three-d`; `islands`/`shadow-light` contain `chat-islands` (`src/native/smoke-groups.ts:81-89`). Preserve the `StaticServer.hold`, 82-stream regression, smoke recovery/time-budget guards and existing live Publish evidence. Do not reintroduce fixture touch retries.
